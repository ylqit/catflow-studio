# 局部视频编辑输入与执行

新编辑使用 `editContractVersion: 2` 和 `segment-edit-v7`。缺少版本字段的旧请求按旧契约处理，已有任务继续使用冻结的 Prompt、参考和时间范围；重新打开历史任务不会重新编译。

## 当前修改方案

修改目标、保留内容、起始状态、动作过程、期望结束状态和需要避免的问题来自同一份可编辑输入。当前文字优先于参考视频中的冲突状态。模板不根据关键词推断编辑目标，也不统一要求运动或静止。

“AI 整理修改方案”是显式创建的 `plan_video_edit` 任务，会调用规划模型并产生费用。输入冻结实际来源时间线、选区内按序抽取的帧和可追溯的历史意图。建议结果先展示，点击填入只采用文字，随后仍可编辑；选区、生成模式和参考选择由用户调整。来源变化后，原建议保留展示，但不能直接采用到新来源。

## 结束策略和参考

| 策略 | 普通片段编辑 |
|---|---|
| `follow_instruction` | 新编辑默认，按当前修改文字结束，不发送原出点图片 |
| `match_original` | 明确保留原结束状态，显示并发送出点衔接图片 |
| `replace` | 必须填写新的结束状态，不发送原出点图片 |

普通入点图片可关闭。草稿中已有的冻结角色、比例、环境和画风参考默认选中，可以逐项排除。缺少历史参考时不从项目当前选择中补齐。实际图片数量按接口能力校验，发送顺序与最终指令中的编号一致。

“从正确起点重新生成”使用用户选定的首帧，不携带原动作视频和上述身份参考。完整取用输出时才可使用严格尾帧；需要裁去额外输出时间时，使用首帧及文字结束目标。

## 三种时间范围

- **草稿替换区间**：1–360 帧、24 fps，右端不包含。该长度决定接回时替换多少帧。
- **来源参考区间**：默认取满足接口输入能力的最小范围；可以选择仅选区或自行设置上下文。上下文必须包含选区并位于实际输入时间线内，不能用复制帧或变速补足。
- **候选取用区间**：长度始终等于替换长度。Provider 输出为 4–15 秒，完整输出保留；用户可以移动取用起点，重新生成本地接回预览。

继续修改候选时，参考取自上一结果接回后的完整时间线。原声或候选声音由用户选择。应用、正式选择和导出继续使用既有人工操作。

第三集末镜头 `[278, 361)` 为 83 帧。新默认参考区间就是该选区，生成 4 秒，默认取用候选 `[0, 83)`；不会将草稿第 360 帧作为结束图片发送。完整候选仍可供人工查看和改变取用位置。

## 冻结、保存与恢复

素材准备的 `mediaInputHash` 只包含来源、范围、选定参考及提取参数。修改文字会使最终指令预览失效，但复用已准备的素材。素材事实和最终 `compiledProviderPrompt` 一同进入提交哈希；Worker 原样发送冻结文本。

`PATCH /api/v1/projects/{project_id}/video-edit-drafts/{draft_id}/input` 使用 `expectedRevision` 保存 `editingInput`。输入修订与草稿视频版本分离。发生版本冲突时保留当前输入，用户读取已保存输入进行比较后再选择；保存不表示采用候选或认可内容。

输入自动保存按原项目、草稿和视频版本保留独立快照。切换草稿会继续保存离开前的输入；保存期间新增的文字使用返回的修订号接续保存，不会写入新打开的草稿。失败时显示恢复提示，当前页面保留未保存内容，可返回重试或处理冲突。成功保存的输入可在刷新后恢复；保存失败时的页面内保留不等于离线持久化。

新增 AI 任务通过 `POST /api/v1/projects/{project_id}/video-edits/plans` 创建，沿用 Job 查询、事件、费用记录、恢复和取消机制。结果使用 `VideoEditPlanSuggestion`，在 `result.editPlan` 中读取。

数据库迁移为 `0034_video_edit_input`，增加草稿输入与输入修订字段，以及新任务类型。API 和 Worker 需要同时使用新代码。现有本地启动脚本会在启动时执行迁移。

## 提交结果待核实与人工恢复

当前方案、所选任务的只读详情分别展示。任务详情只读取提交快照中的来源结果、参考准备任务、素材、区间和最终 Prompt；旧 URL 中的参考任务不会替换这些事实。查看任务不改变当前方案，只有点击“复用参数到当前修改方案”才同时恢复文字和素材关联。异步恢复期间若输入变化，恢复操作不会覆盖新输入。

建议保存、参考素材准备、视频下载保存和接回预览分别显示具体阶段。`submission_unknown` 统一展示“提交结果待核实”，仍阻止未经确认的重复生成。AI 整理仅产生文字建议；免费参考准备仍为独立入口。

`GET /api/v1/jobs/{job_id}/provider-tasks` 为只读核对，按任务冻结模型及提交开始前 2 分钟、后 15 分钟的窗口查询。最多读取 5 页，每页 50 个任务。返回 `query_failed`、`not_found` 或 `candidates`，并用 `coverageComplete` 标明是否完整扫描；候选只是可能相关，系统不会自动关联。查询和恢复不调用生成接口。

人工核对任务编号后，可通过既有 `POST /api/v1/jobs/{job_id}/recovery` 提交 `action: associate_provider_task`、`providerTaskId`、`confirmAssociation: true`、`acknowledgeUnverifiedParameters: true`，以及 `expectedRevision` 和 `idempotencyKey`。服务端重新查询、比较已知冻结参数，并原子校验任务修订、租约及重复关联；成功后沿用原任务的查询、回执和结果落地链路。已提交成功的相同恢复请求直接复用保存的操作记录，不依赖云端再次可用。

云端接口不能完整证明 Prompt、参考素材身份和未返回参数，所以关联必须由用户明确确认。未找到确切任务时，原记录继续保留为未知；如用户决定付费重建，继续使用已有的显式重复收费确认流程。

新的提交诊断记录 `connect`、`write`、`read`、`pool` 或 `unknown` 超时类别，以及请求体字节数、参考图片／视频数量、准备与提交耗时、客户端／服务端追踪号。实际 HTTP 请求大小与 JSON 估算值明确区分；不保存 Base64、凭据或签名地址。原始 SDK 异常链可能回显请求数据，因此视频提交错误采用脱敏消息和结构化异常类型作为持久化及日志证据。传输方式和默认 120 秒请求超时保持不变。
